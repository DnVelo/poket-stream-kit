手を動かす前に、**その目的の仕組みが既にあるか**を探すこと。
特に「上流のビルドシステムの設定項目」「build.zig のオプション」「本家ツールの実装」。

🔴 **同じ役目の既存ファイルに書いてある注意書きは、過去の記録ではなく「新しいコードへの制約」。**

**Why:** 3 回同じ形で外した。

1. (2026-08-28) CraftJuke OS 向けに素の `zig build` を叩き、Debian 側の
   `libvpx.so.9` にリンクされて起動しなかった。⚠ `build.zig` には
   **`-Dsysroot=` が用意され、コメントで使い方まで書いてあった**。
2. (2026-08-28) getty を1つにするのに `post-build.sh` の `sed` で inittab を細工した。
   ⚠ Buildroot には **`BR2_TARGET_GENERIC_GETTY_PORT`** がある。
   しかも私の細工は前提が誤っていて、**唯一の getty を消していた**。
3. (2026-08-30) Linux のパッド対応で、描画スレッドに **1秒ごとの `/dev/input` 再スキャン**を書き、
   実機で 1 秒周期のプチフリーズになった。⚠ 同じ機能の `input_driver_evdev.cpp` に
   **「定期的に呼ぶのも駄目。呼ぶのは inotify が鳴ったときだけ」**と、実機で踏んだ経緯つきで
   書いてあった。⚠ その注意書きは**作業中に実際に読んでいた**のに、
   「昔そうだった話」として通過した。Windows の `compat_dinput.cpp` も同じ結論
   （列挙は専用スレッドへ逃がし、ホットパスでは走らせない）。

⭐ どれも「先に探せば 1 分で済み、しかも壊さずに済んだ」。
⚠ 自前の細工は上流が変わると空振りし、**空振りしても気づけない**のが最悪の性質。

**How to apply:**
- ⭐ 設定を変えたくなったら、まず `grep` で**その名前の設定項目**を探す
  （`Config.in` / `build.zig` / 本家スクリプト）。
- ⭐ **同じ役目の既存実装を先に開き、その 🔴/⚠ を「これから書くコードの禁止事項」として読む。**
  ⚠ 「読んだ」で終わらせない。新しいコードがその禁止に触れていないかを書いた後に照合する。
- ⭐ 「本家はどうやっているか」を読む。推測で埋めない。
- ⚠ どうしても自前で作るなら、**なぜ既存では駄目か**をコメントに残す。
