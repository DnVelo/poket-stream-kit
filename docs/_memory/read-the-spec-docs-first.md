数値・仕様・過去の決定を根拠にするときは、**必ず `Gear-vk/docs/` の該当章を読む**。
CLAUDE.md のルール（確定スペックは `GEAR_*.md` が source of truth・まず README・1タスク2ファイルまで）を
長いセッションの途中で忘れやすい。

**Why:** 2026-08-28、動画が再生できない件で「ベンチは HEVC だから VP9 の実測は無い」と結論したが、
⚠ 根拠にしたのは `tools/media/make_bench_video.sh` の**ヘッダコメント**だった。
実際は `docs/2_impl/GEAR_PORTING.md` に **「VP9 1080×1920 を 1スレッド 0.41 コア＝実時間の 2.45 倍速」**
と明記されており、スクリプトの方が古い残骸だった。
⚠ しかも `vpxvideo.zig` のコメント自身が **「詳細 `GEAR_LICENSES §4.4`」** と行き先を書いていた。
⭐ 一次資料が名指しされているのに、たまたま目に入ったファイルを根拠にした。

同じ日に推測で3回外している（レーン数と色数の混同・`-Dsysroot` の見落とし・ベンチ条件の誤認）。
⚠ どれも「既にある情報を確かめる前に動いた」点で同じ。

🔴 **自分が書いたコメントを根拠にしない。** 2026-08-30、LIGHT 3L のデモ抽選で
「先読みは解析までで畳まない」とコメントにも資料にも書いたが、**確かめずに書いた嘘**だった。
実際は `prefetcher.h` が `gear_game_create` を丸ごと先に走らせて Game を作り置きしている。
⚠ その後の調査で私は**自分のコメントを事実として読み直し**、原因を取り違えた。
⚠ 断定を書くとそれが次の自分の前提になるので、**未確認の断定はコメントにも資料にも書かない**
（書くなら「未確認」と添える）。

**How to apply:**
- ⭐ 数値を引用する前に `grep -rn "<その数値>" docs/` を打つ。書いてあることが多い。
- ⭐ コードのコメントが資料の節を名指ししていたら、**そこを開く**。
- ⚠ ツールやスクリプトのコメントは**古びている前提**で扱う。正は `GEAR_*.md`。
- ⚠ 長いセッションでは特に忘れる。行き詰まったら「資料を読んだか？」を自問する。
- 🔴 **仕組みの挙動を断定する前に、その実装ファイルを開く**（`prefetcher.h` を開けば1分で済んだ）。
