## 1. 技術スタック

### 1.1 🟢 方針（2026-10-14 決定）
- 🟢 **Zig ＋ C++ の構成**（Gear-vk と同じ）。**極力 Zig で書き、C++ は避けられない所だけ**。
- 🟢 **目的は徹底した軽量化**。CPU とスケジューリングに余裕を作り、**ASIO のバッファを限界まで切り詰められる**ようにする。
- ❌ JUCE（叩き台）は不採用[^juce]。
- ⭐ **将来の Android 移植に備える**（2026-10-14 ユーザー要望）。オーディオ層は移植しやすい形にする。

### 1.2 各部をどう書くか
| 部分 | 方針 | 備考 |
|---|---|---|
| 🟢 ASIO | **Zig から ASIO ドライバの COM インターフェースを直接呼ぶ**（2026-10-14 決定） | RtAudio は使わない[^rtaudio-api]。🔴 x64 の素の COM として呼べるかは未検証 |
| 🟢 ASIO 以外の入出力 | **miniaudio**（C・Zig から `@cImport`）（2026-10-14 決定） | 仮想ケーブルの入出力すべて。Android（AAudio / OpenSL ES）にもそのまま使える[^gear-audio] |
| 🟡 VST3 ホスト | Steinberg の C 版ヘッダ（`vst3_c_api`）を Zig から使う／VST3 SDK（C++）の薄い層 | 🔴 C 版ヘッダで実用のホストが組めるかは未検証 |
| 🟡 画面 | Zig から Win32 を直接呼ぶ | プラグインのエディタも Win32 のウィンドウに載せる |

- 🟢 Android へ移植するときは、ASIO の部分を外して miniaudio だけで動かす。⚠ VST3 も Android には無いので、プラグインの扱いは移植時に別途決める。
- ⚠ Gear-vk では ASIO（RtAudio 経由）と miniaudio を**同時には開かない**設計だった[^gear-audio]。本ツールは **ASIO と miniaudio を同時に開くのが本題**なので、そこは新しく作る部分になる。
- ⚠ ASIO SDK のライセンス: Gear-vk の資料では「再配布不可」だが、**2.3.4（2025-10-15）から Steinberg 独自ライセンスと GPLv3 の選択制**になった[^asio-license]。

## 2. 信号経路

### 2.1 🟢 声（必須の部分）
```
ASIO in ─▶ [プラグインチェーン] ─┬─▶ ASIO out（ヘッドホン）
                                └─▶ クロック橋渡し ─▶ WASAPI 共有 / DirectSound out（VB-CABLE → OBS）
```
- 🟡 モニターを「処理後」にするか「処理前（プラグイン遅延ゼロ）」にするかの切り替えを持つか。

### 2.2 🟢 デスクトップ音・通話の取り込み = 仮想ケーブル経由（2026-10-14 決定）
- 🟢 各アプリ（ブラウザ・ゲーム・Discord など）の出力先を仮想ケーブルにし、本ツールがその録音側を入力として読む。
- 🟢 仮想ケーブルを Windows の既定のスピーカーにすれば、出力デバイスの音を丸ごと拾うのと同じことができる[^cable-default]。
- 🟡 入力として読むケーブルの数も、出力と同じく増やせるようにするか。

### 2.3 出力先（ストリーム）
- 🟢 **出力先は必要な数だけ増やせる**（2026-10-14 決定）。VB-CABLE 類は最大5本まで使える[^cable-count]。
- 🟢 用途は OBS 向けと、Discord などの通話アプリのマイク向け。
- 🟡 通話相手へ送る音の中身（処理後の声だけか。通話の音そのものを混ぜない＝相手に自分の声が返らない構成にするか）。

### 2.4 🟢 OBS へ送る形 = 全部を混ぜた1本（2026-10-14 決定）
- 🟢 基本は、声・デスクトップ音・通話を混ぜて1本で送る。

## 3. デバイスとクロック

### 3.1 🟢 ASIO ドライバ = Creative ASIO（2026-10-14 決定）
- 🟢 **Play! 3 の Creative ASIO を使う**。ASIO4ALL は使わない。
- 🟢 X390 への導入と動作は**ユーザーが確認済み**（導入手順はユーザーが参照した note の記事[^creative-asio]）。
- 🔴 **完全な排他か、ASIO 以外の音も同時に Play! 3 から鳴らせるかは未検証**。ヘッドホンへ返す音の設計（`PSK_VISION §3.3`）がこれで変わる。
- 🟡 使えるバッファサイズとサンプルレートは未確認。

### 3.2 🟢 クロックの橋渡しは必須
- ASIO 側（Play! 3）と各仮想ケーブルは**別のクロック**で動くので、デバイスごとにずれを吸収する仕組みが要る。
  ⚠ 入力側のケーブル（デスクトップ音・通話）も同じで、ASIO のクロックへ合わせ込む必要がある。
- 🟡 方式は未決。参考に、叩き台（削除済み）で試した方式を残す[^driftfifo]:
  - 書き手と読み手が1つずつのリングバッファ。読み手側で **4点エルミート補間**のリサンプラーを回す。
  - 再生速度 ＝ 公称レート比 ×（1＋補正）。補正は **FIFO の水位の誤差に対する PI 制御**で決める（48k⇔44.1k のような公称レートの違いも同じ仕組みで吸収する）。
  - 起動時とアンダーラン時は、目標の水位まで溜めてから鳴らし始める。
  - ⚠ 制御の係数と上限値は叩き台で置いた値で、**根拠は無い**（実機で決める）。
  - 🟢 シミュレーションの結果: クロックが ±200ppm ずれる条件と 48k⇔44.1k を含む5ケースで、水位は目標 30ms の ±0.4ms に収まり、安定後の音切れは0回、SNR は約 100dB（2026-10-14）。

### 3.3 🟢 遅延を詰めるのはモニターだけ（2026-10-14 決定）
- 🟢 **低遅延が要るのはヘッドホンへのモニター（ASIO）だけ**。OBS や通話アプリへの出力、仮想ケーブルからの入力は、バッファを切り詰めなくてよい。
- ⭐ その分の余裕は、ASIO のコールバックを軽く保つことに回す（重い処理を ASIO のコールバックの外へ出せるか、は §4 で検討）。
