## 1. 技術スタック

### 1.1 🟢 方針（2026-10-14 決定）
- 🟢 **Zig ＋ C++ の構成**（Gear-vk と同じ）。**極力 Zig で書き、C++ は避けられない所だけ**。
- 🟢 **目的は徹底した軽量化**。CPU とスケジューリングに余裕を作り、**ASIO のバッファを限界まで切り詰められる**ようにする。
- ❌ JUCE（叩き台）は不採用[^juce]。
- ⭐ **将来の Android 移植に備える**（2026-10-14 ユーザー要望）。オーディオ層は移植しやすい形にする。

### 1.2 各部をどう書くか
| 部分 | 方針 | 備考 |
|---|---|---|
| 🟢 ASIO | **Zig から ASIO ドライバの COM インターフェースを直接呼ぶ**（2026-10-14 決定） | RtAudio は使わない[^rtaudio-api]。🔴 x64 の素の COM として呼べるかは未検証 |
| 🟢 ASIO 以外の入出力 | **miniaudio**（C・Zig から `@cImport`）（2026-10-14 決定） | 仮想ケーブルの入出力すべて。Android（AAudio / OpenSL ES）にもそのまま使える[^gear-audio] |
| 🟡 VST3 ホスト | Steinberg の C 版ヘッダ（`vst3_c_api`）を Zig から使う／VST3 SDK（C++）の薄い層 | 🔴 C 版ヘッダで実用のホストが組めるかは未検証 |
| 🟡 画面 | Zig から Win32 を直接呼ぶ | プラグインのエディタも Win32 のウィンドウに載せる |

- 🟢 Android へ移植するときは、ASIO の部分を外して miniaudio だけで動かす。⚠ VST3 も Android には無いので、プラグインの扱いは移植時に別途決める。
- ⚠ Gear-vk では ASIO（RtAudio 経由）と miniaudio を**同時には開かない**設計だった[^gear-audio]。本ツールは **ASIO と miniaudio を同時に開くのが本題**なので、そこは新しく作る部分になる。
- ⚠ ASIO SDK のライセンス: Gear-vk の資料では「再配布不可」だが、**2.3.4（2025-10-15）から Steinberg 独自ライセンスと GPLv3 の選択制**になった[^asio-license]。

## 2. 信号経路

### 2.1 🟢 声（必須の部分）
```
ASIO in ─▶ [プラグインチェーン] ─┬─▶ ASIO out（ヘッドホン）
                                └─▶ クロック橋渡し ─▶ WASAPI 共有 / DirectSound out（VB-CABLE → OBS）
```
- 🟡 モニターを「処理後」にするか「処理前（プラグイン遅延ゼロ）」にするかの切り替えを持つか。

### 2.1b 🟢 全体の形 = 送り量の表を持つミキサー（2026-10-14 決定）
```
入力                                  出力
・マイク（ASIO）→ プラグインチェーン    ・ヘッドホン（ASIO）
・ケーブル入力 1〜n（miniaudio）        ・ケーブル出力 1〜m（miniaudio）
                 └──── 送り量の表（入力 × 出力）────┘
```
- 🟢 **仮想ケーブルは入力と出力で合わせて最大5本**（n＋m ≦ 5）。VB-CABLE 類は1本が「音を入れる側」と「録音する側」の組で、取り込みにも1本ずつ使うため。
- 🟢 出力ごとに「どの入力をどれだけ混ぜるか」を表で持つ。OBS 向けは全部を混ぜ、通話アプリ向けは通話の入力を 0 にする（相手に自分の声が返らない）、のように表の値だけで決める。
- 🟢 プラグインチェーンはマイクの後ろに1本だけ。ミキサーに入る前に処理を済ませる。

### 2.2 🟢 デスクトップ音・通話の取り込み = 仮想ケーブル経由（2026-10-14 決定）
- 🟢 各アプリ（ブラウザ・ゲーム・Discord など）の出力先を仮想ケーブルにし、本ツールがその録音側を入力として読む。
- 🟢 仮想ケーブルを Windows の既定のスピーカーにすれば、出力デバイスの音を丸ごと拾うのと同じことができる[^cable-default]。
- 🟢 入力として読むケーブルも本数を増やせる（§2.1b の n 本）。

### 2.3 出力先（ストリーム）
- 🟢 **出力先は必要な数だけ増やせる**（2026-10-14 決定）。VB-CABLE 類は最大5本まで使える[^cable-count]。
- 🟢 用途は OBS 向けと、Discord などの通話アプリのマイク向け。
- 🟢 通話相手へ送る音の中身は仕様で固定しない。送り量の表（§2.1b）で使う人が決める。

### 2.4 🟢 OBS へ送る形 = 全部を混ぜた1本（2026-10-14 決定）
- 🟢 基本は、声・デスクトップ音・通話を混ぜて1本で送る。

## 3. デバイスとクロック

### 3.1 🟢 ASIO ドライバ = Creative ASIO（2026-10-14 決定）
- 🟢 **Play! 3 の Creative ASIO を使う**。ASIO4ALL は使わない。
- 🟢 X390 への導入と動作は**ユーザーが確認済み**（導入手順はユーザーが参照した note の記事[^creative-asio]）。
- 🔴 **完全な排他か、ASIO 以外の音も同時に Play! 3 から鳴らせるかは未検証**。ヘッドホンへ返す音の設計（`PSK_VISION §3.3`）がこれで変わる。
- 🟡 使えるバッファサイズとサンプルレートは未確認。

### 3.2 🟢 クロックの橋渡しは必須
- ASIO 側（Play! 3）と各仮想ケーブルは**別のクロック**で動くので、デバイスごとにずれを吸収する仕組みが要る。
  ⚠ 入力側のケーブル（デスクトップ音・通話）も同じで、ASIO のクロックへ合わせ込む必要がある。
- 🟡 方式は未決。参考に、叩き台（削除済み）で試した方式を残す[^driftfifo]:
  - 書き手と読み手が1つずつのリングバッファ。読み手側で **4点エルミート補間**のリサンプラーを回す。
  - 再生速度 ＝ 公称レート比 ×（1＋補正）。補正は **FIFO の水位の誤差に対する PI 制御**で決める（48k⇔44.1k のような公称レートの違いも同じ仕組みで吸収する）。
  - 起動時とアンダーラン時は、目標の水位まで溜めてから鳴らし始める。
  - ⚠ 制御の係数と上限値は叩き台で置いた値で、**根拠は無い**（実機で決める）。
  - 🟢 シミュレーションの結果: クロックが ±200ppm ずれる条件と 48k⇔44.1k を含む5ケースで、水位は目標 30ms の ±0.4ms に収まり、安定後の音切れは0回、SNR は約 100dB（2026-10-14）。

### 3.3 🟢 遅延を詰めるのはモニターだけ（2026-10-14 決定）
- 🟢 **低遅延が要るのはヘッドホンへのモニター（ASIO）だけ**。OBS や通話アプリへの出力、仮想ケーブルからの入力は、バッファを切り詰めなくてよい。
- ⭐ その分の余裕は、ASIO のコールバックを軽く保つことに回す（重い処理を ASIO のコールバックの外へ出せるか、は §4 で検討）。

## 5. 🟡 プラグイン
- 🟡 今の FL Studio のチェーン（ユーザーの記憶・2026-10-14・「間にコンプも挟まっていたかも」）:
  **EQ → RX 8 → rovee → Soundgoodizer → EQ → T-De-Esser**
- 🔴 Soundgoodizer は FL Studio に内蔵のプラグインで、ほかのホストでは使えない見込み。

### 5.1 🟢 各段の扱い（2026-10-14 ユーザー回答）
| 段 | 中身 | 扱い |
|---|---|---|
| ノイズ除去 | **iZotope RX 8 の Voice De-noise だけ** | 🟢 そのまま使う（プラグインとしてホストする） |
| ボイスチェンジャー | **rovee（g200kg 製）** | 🟢 **必須**（他のボイチェンでは好みの音にならなかった）。🟡 かなりシンプルなので**内製も検討**。🟢 **32bit 専用の VST2**[^rovee-dll]（§5.2） |
| ディエッサー | T-De-Esser | 🟢 **できれば使いたい**。🟡 内製できるなら、**聞き比べて決める**（2026-10-14 ユーザー回答）。🔴 形式（VST3 か・64bit か）は未確認 |
| EQ・コンプ・マキシマイザーなど | こだわりなし | 🟢 **汎用のもので構わない** |

- 🟡 汎用の段（EQ・コンプ・マキシマイザー）を、本ツールに内蔵するか、無料の VST3 で済ませるか。
- 🟡 rovee を内製するか、プラグインとしてホストするか（§5.2）。

### 5.2 🟢 rovee の素性（2026-10-14 に DLL を調べた結果）
- 🟢 **32bit（x86）の VST2 プラグイン**。VST SDK 2.4 で作られている[^rovee-dll]。
- ⚠ **64bit のプロセスからは 32bit の DLL を直接読み込めない**。本ツールを 64bit で作るなら、ホストするには「32bit の別プロセスを立てて音をやり取りする」橋渡しが要る（遅延と複雑さが増える）。FL Studio では FL 自身の橋渡し機能で動いていたはず。
- 🔴 RX 8 が 64bit 専用かは未確認。64bit 専用なら、本ツールを 32bit にして rovee を直接読む道も閉じる。
- 🟢 パラメータ名（DLL 内の文字列）: **Mix・Pitch・Robot・Formant**。設定ファイル `RoVee.ini` の `[midicc]` 節には、これに Vol・Bal・Mod・BndRng を加えた8つがある。
- 🟡 `RoVee.ini` の `[midicc]` 節（Vol=7・Bal=10・Mod=41・BndRng=14・Mix=19・Pitch=26・Formant=29・Robot=23）が何を表すかは**未確定**:
  - 設定値（つまみの位置）とみる根拠: ユーザーの観察（2026-10-14・「Mix〜Robot がそのまま設定値っぽい」）。
  - MIDI CC の割り当てとみる根拠: 節の名前が `midicc`・DLL に MIDI を受け取る処理がある・Vol=7／Bal=10 が MIDI の慣例（CC7＝ボリューム・CC10＝パン）と一致・BndRng の選択肢は 0〜12 の13個で `14` は範囲外。
  - ini は rovee 自身が書き込んでいる（`WritePrivateProfileStringA` を使用）。
  - 🟡 確かめ方: FL Studio で Pitch を動かして保存し、ini の `Pitch=` が変わるかを見る。

## 6. 操作と UI
- 🟢 **操作はすべて X390 の画面で行う**（2026-10-14 決定）。リモート操作は作らない。
- 🟡 ホットキーや OBS との連携が要るか。

### 6.1 🟢 画面の形 = チャンネルストリップを横に並べる（2026-10-14 ユーザーのスケッチ[^ui-sketch]）
1本のチャンネル（縦長）を上から:

| 位置 | 部品 | 中身 |
|---|---|---|
| 1 | **in** | 入力の選択（マイク＝ASIO／ケーブル入力） |
| 2 | **fx** | エフェクトのスロット（スケッチでは**6段**） |
| 3 | **フェーダー** | 目盛りは **+10 ／ 0 ／ −∞**（🟡 単位は dB と読んだ・要確認） |
| 4 | **out** | 出力先の選択 |
| 右端 | **メーター** | チャンネルごとの縦長メーター（下から緑・黄・赤） |

- 🟡 **out は1つだけ選ぶのか、複数に送れるのか**。§2.1b の「送り量の表」とのすり合わせが要る（例: 声はヘッドホンと OBS の両方へ送る）。
- 🟡 **エフェクトのスロットが全チャンネルにある**＝§2.1b の「チェーンはマイクの後ろに1本だけ」と食い違う。全チャンネルに持たせるか。
- 🟡 出力側（ヘッドホン・各ケーブル）にもフェーダーとメーターを持つか。
- 🟡 メーターの色の境目（何 dB から黄・赤か）は未決。
